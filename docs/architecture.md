# SI-RVP Architecture

This document mirrors §III of the IEEE Access manuscript. It describes
the on-chain contracts, the off-chain components, and the commitment
that binds them together.

## On-chain components

```
L1 Ethereum
├── RollupManager        — receives state-root proposals from the sequencer
├── DisputeGameFactory   — EIP-1167 minimal-clone factory (Optimism IDisputeGame compatible)
├── ZKDisputeGameProxy   — IDisputeGame -> DisputeManager adapter
├── DisputeManager       — dispute lifecycle (challenge, bond, bisection commit, proof, resolve)
├── ZKVerifier           — wraps Groth16Verifier; converts public-input arrays
└── Groth16Verifier      — auto-generated by snarkjs from the circom MIPS-step circuit
```

The protocol exposes itself through the standard Optimism `IDisputeGame`
interface via `ZKDisputeGameProxy`, so an existing Optimism-style
factory deployment can register SI-RVP as one of its game types
without forking core dispute logic. See §III.D of the paper for the
Optimism-compatibility derivation.

## Off-chain components

- **Sequencer** — proposes batches, signs bisection moves when
  challenged. Code: [`node/src/sequencer/`](../node/src/sequencer).
- **Challenger** — monitors L1 for new state roots, verifies them
  locally, and initiates a dispute when divergence is found. Code:
  [`node/src/challenger/`](../node/src/challenger).
- **Prover** — generates the Groth16 single-step proof at the
  disputed instruction. Code: [`node/src/common/prover.ts`](../node/src/common/prover.ts).
- **P2P bisection transport** — exchanges signed bisection moves
  off-chain. Code: [`node/src/common/p2p.ts`](../node/src/common/p2p.ts)
  and [`node/src/common/bisection.ts`](../node/src/common/bisection.ts).

The bisection runs entirely off-chain over P2P. Each move is a signed
message containing a Poseidon hash of the disputed half-trace's
endpoints; only the terminal commitment — the Poseidon hash binding
the disputed single-instruction state transition — reaches L1.

## Bisection-to-ZK commitment

The critical alignment between off-chain bisection and on-chain proof
verification lives in [`contracts/src/DisputeManager.sol`](../contracts/src/DisputeManager.sol)
around the `submitProof` path. The off-chain bisection's terminal
state hash is recomputed inside the circuit as a public input, so a
Groth16-valid proof is *only* accepted if its public input matches
the value the on-chain `DisputeManager` already committed to during
bisection-result submission. This closes the soundness gap that
earlier hybrid sketches had between "bisection narrowed to step k"
and "proof claims correctness at step k".

See §III.C of the paper for the formal statement and §IV.B for the
reduction argument.

## Trust model

SI-RVP preserves the 1-of-N permissionless trust model:

- The validator pool is permissionless. Any participant can run the
  challenger software and stake the bond.
- Safety holds as long as at least one honest validator (1-of-N) is
  online during the dispute window. An off-chain validator failure
  triggers a fallback to the next available challenger, with the
  on-chain dispute clock continuing uninterrupted.

This is in contrast to "permissioned multi-party" trust models where
a fixed council resolves disputes. See §III.E of the paper for the
instance-versus-pool distinction.

## What lives where

| Concern | Location |
|---------|----------|
| State-root submission | `contracts/src/RollupManager.sol` |
| Dispute initiation, bonds | `contracts/src/DisputeManager.sol` |
| ZK proof verification | `contracts/src/ZKVerifier.sol` (wraps `Groth16Verifier.sol`) |
| Optimism-factory adapter | `contracts/src/ZKDisputeGameProxy.sol`, `DisputeGameFactory.sol` |
| MIPS single-step circuit | `circuits/src/mips_single_step.circom` |

| Groth16 proof generation | `node/src/common/prover.ts` |
| End-to-end demo + benchmarks | `node/src/scripts/onchain-e2e.ts` |
